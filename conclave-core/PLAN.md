# conclave-core — план

> Статус: **P0–P5 + stateless + S1–S5 реализованы**, плюс написан локальный
> агент с Web UI в соседнем модуле **`conclave-agent`** (два WS, локальные
> инструменты, SSE-UI). См. README.md и §18.
> Область: **только ядро**. Локальный агент (`conclave-agent`) и UI — отдельные
> будущие проекты, здесь не разрабатываются.

---

## 1. Идея

`conclave-core` — облачное **ядро оркестрации нейросетей** для выполнения задач
по разработке и смежным дисциплинам. Пользователь формулирует идею, ядро:

1. уточняет требования (интервью),
2. строит **план из плейбуков** (граф),
3. запускает плейбуки параллельно/последовательно,
4. периодически перепланирует,
5. проверяет результат критиком,
6. задаёт вопросы пользователю или отвечает рекомендованным вариантом,
7. выполняет работу через локального агента (файлы/exec) и внутренние
   инструменты (поиск/калькулятор/анализ).

Ключевая продуктовая идея: **готовые плейбуки, которые минимизируют участие
человека**, с экономией за счёт разных моделей под разные уровни задач
(junior/middle/senior) и иерархии контроллеров.

### Базовые плейбуки (стартовый набор)

- Backend разработка
- Frontend разработка
- Web-дизайн
- Бизнес-анализ (BA)
- IT-архитектура
- DBA-инженерия
- Security review
- General purpose
- …и другие по мере развития

Каждый плейбук состоит из **ролей** (например, backend = senior/middle/junior),
каждая роль привязана к своей модели. Внутри плейбука есть **диспетчер**,
который раскидывает задачи по ролям-уровням.

## 2. Границы

### В scope (этот проект)
- Ядро: интервью, планирование, планировщик, исполнение, критик, вопросы.
- Облачная инфраструктура: Postgres, Redis, object storage.
- Протокол связи с локальным агентом (серверная сторона + codec).
- Реестр плейбуков и их версий.
- Eval-harness для измерения качества плейбуков.
- Мульти-тенантность, device-токены, бюджеты/квоты.

### Вне scope (будущие проекты)
- `conclave-agent` — реализован: локальный исполнитель (fs/exec/git/patch),
  два WebSocket-соединения и встроенный Web UI. См. `conclave-agent/README.md`.
- UI (граф, таймлайны, история MCP/диалогов) — позже; ядро отдаёт read-model API.
- Маркетплейс плейбуков, биллинг, self-host/on-prem, мульти-регион.

## 3. Принципы

1. **Всё в облаке.** LLM, оркестрация, состояние. Локально — только исполнитель.
2. **Event-sourced.** План, сессии, задачи — append-only лог событий; граф и
   таймлайны — проекции. Восстановление после сбоя и реконнекта «бесплатно».
3. **Иерархия вместо одного контроллера.** Топ-планировщик редкий и дорогой,
   супервизоры на плейбук дешевле, диспетчер — на одну задачу.
4. **Два уровня графа.** Крупный план плейбуков и мелкий граф задач внутри
   плейбука. Нейросети видят только релевантный уровень/подграф.
5. **Human-gate не блокирует.** Ожидание ответа пользователя не останавливает
   параллельные ветки.
6. **Реконнект = пауза + reconcile.** Разрыв связи ставит сессию на паузу;
   незавершённые вызовы сверяются и ретраятся.
7. **Безопасность по умолчанию.** В ядре не исполняется пользовательский код;
   секреты провайдеров не покидают ядро.
8. **Измеримость.** У ядра есть eval-контур для проверки качества и регрессий
   (вне шаблона плейбука).
9. **Идемпотентность.** Внешние вызовы (tool-calls к агенту) идемпотентны по
   ключу; повтор безопасен.
10. **Наблюдаемость.** OTel-трейсы и метрики на каждый шаг, вызов, задачу.

## 4. Пользовательский сценарий (сквозной)

Пример: «хочу сделать интернет-магазин».

1. **Интервью.** Interviewer задаёт уточняющие вопросы: стек, есть ли готовый
   дизайн, нужен ли анализ рынка, целевая платформа и т.п. Формируется `Spec`
   (требования, ограничения, acceptance).
2. **План.** Planner строит `Plan v1` — граф плейбуков с типами связей:
   - BA (если нужен анализ рынка — иначе вопрос пользователю),
   - параллельно: Web-дизайн + IT-архитектура,
   - после архитектуры: DBA + Backend (параллельно/последовательно),
   - после дизайна: Frontend,
   - Security review в конце,
   - General purpose для вспомогательных задач.
3. **Исполнение.** Каждый плейбук — свой тред. Дизайн по завершении уходит на
   human-gate (одобрение), **не блокируя** остальные ветки. Плейбук может ждать
   завершения другого (dependency) или его артефакт (data edge).
4. **Диспетчер.** Внутри backend-плейбука диспетчер разбивает работу на задачи и
   раздаёт: «эти 10 — сеньорам, эти 10 — джунам».
5. **Перепланирование.** На чекпоинтах Planner/Supervisor вносит корректировки
   в граф (добавить/убрать/переставить узлы).
6. **Критик.** Проверяет объективно (сборка/тесты/линтер) и по спеке; может
   переоткрыть задачи.
7. **Вопросы.** Любой плейбук может задать вопрос. Если включён
   auto-accept — ядро само отвечает **первым (рекомендованным)** вариантом.
8. **Результат.** Артефакты, отчёты, полный таймлайн.

## 6. Доменная модель

Иерархия:

```
Tenant ─▶ User ─▶ Project ─▶ Session ─▶ Plan (versioned)
                                        └─▶ PlaybookRun (thread)
                                              └─▶ Task ─▶ Attempt
```

| Сущность | Описание |
|---|---|
| **Tenant** | Изолированный клиент (организация/аккаунт). |
| **User** | Пользователь внутри тенанта. |
| **Device** | Устройство пользователя с device-токеном; позже — точка подключения агента. |
| **Project** | Рабочее пространство (репозиторий/набор файлов) на стороне агента. |
| **Session** | Одна задача пользователя; агрегат всего состояния. |
| **Spec** | Версионируемые требования, ограничения, стек, acceptance (результат интервью). |
| **Plan** | Версионируемый граф плейбуков; мутирует контроллер. |
| **PlanNode** | Экземпляр плейбука в плане (`PlaybookRun`), узел графа. |
| **PlanEdge** | Связь: `dependency` \| `data` \| `review`. |
| **Playbook** | Шаблон (реестр, версии): входы/выходы, роли, гайдлайны, control, question_policy. |
| **PlaybookRun** | Запущенный плейбук: тред, стейт-машина, артефакты, вопросы, стоимость. |
| **Task** | Единица работы внутри плейбука; назначена роли-тиру; попытки. |
| **Attempt** | Одна попытка выполнения задачи (для эскалации/ретраев). |
| **Role / Tier** | junior/middle/senior (и иные), модель, инструменты, права. |
| **Artifact** | Именованный результат (spec/plan/design/diff/test-report). |
| **Question** | Вопрос пользователю: scope, варианты (рекомендованный первым), политика. |
| **Event** | Append-only запись: seq, тип, payload, корреляция. |
| **Usage** | Токены/стоимость по сессии/плейбуку/задаче. |

### Типы связей в плане
- **dependency** — узел ждёт завершения другого.
- **data** — узел ждёт конкретный артефакт другого.
- **review** — human-gate/approval; **не блокирует** siblings.

## 7. Плейбуки

Плейбук — переиспользуемый шаблон:

```yaml
id: backend
version: 1
title: "Backend Development"
inputs: [spec, architecture]
outputs: [code, tests, api_spec]
roles:
  - { tier: senior,  model: openai/gpt-4o,          tools: [fs, exec, git, tests] }
  - { tier: middle,  model: deepseek/deepseek-chat, tools: [fs, exec, git, tests] }
  - { tier: junior,  model: ollama/qwen2.5-coder,   tools: [fs, tests] }
control: supervisor            # supervisor | explicit-graph
graph: null                    # опциональный явный подграф задач
guidelines: prompts/backend.md # максимум гайдлайнов для контроллера/ролей
question_policy: { auto_accept: inherit, max_questions: 5 }
```

- `control: supervisor` — внутри плейбука работает Supervisor + Dispatcher
  (рекомендуемый режим).
- `control: explicit-graph` — жёстко заданный мини-DAG (для воспроизводимых
  процессов).
- Плейбуки **версионируются**; реестр хранит историю.

### Проверка результата (без жёстких критериев в шаблоне)

В шаблоне плейбука **нет** полей `acceptance`, `budget` и `eval_ref`. Причины:

- Конкретные команды (`go build`, `go test`, `golangci-lint`) могут быть не
  установлены у пользователя, поэтому их нельзя делать обязательными. Ядро
  определяет доступный инструментарий динамически из **capabilities агента**
  (какие языки/сборщики/линтеры есть на машине) и запускает только то, что
  реально доступно. Отсутствие инструмента — не провал, а «недоступная
  проверка».
- Критерии приёмки формирует **Critic** из `Spec` (требований пользователя) и
  контекста задачи, а не из статического списка в плейбуке. Он опирается на
  объективные сигналы (сборка/тесты/линтер — если доступны) и на intent-оценку
  по спеке.
- Лимиты стоимости — на уровне сессии/тенанта (см. раздел 13), а не на уровне
  одного плейбука.
- Eval — отдельный контур ядра (раздел 15), а не поле шаблона плейбука.

## 8. Ядро-мозг (иерархия)

| Компонент | Роль | Дороговизна | Частота |
|---|---|---|---|
| **Interviewer** | Собирает `Spec` из идеи пользователя. | Высокая | Редко |
| **Planner** | `Spec → Plan`, перепланирование на чекпоинтах. | Высокая | По событиям |
| **Supervisor** | Исполняет и мутирует подграф одного плейбука. | Средняя | На плейбук |
| **Dispatcher** | Декомпозиция на задачи, назначение тира, эскалация. | Низкая/средняя | На задачу |
| **Critic** | Objective-first проверка (только доступные инструменты), затем intent по спеке. | Средняя | На чекпоинт |
| **ModelRouter** | Выбор модели под роль/тир с учётом стоимости. | — | На вызов |

**Контекст нейросетей (важно):**
- Planner видит только **сводку** плейбуков (сворачивание), не детали.
- Supervisor видит свой подграф + релевантные артефакты.
- Dispatcher видит одну задачу и её контекст.
- Полный граф хранится в ядре и отдаётся клиенту (UI) позже.

**Гайдлайны.** Для контроллеров пишутся максимально подробные гайдлайны
(структурированные политики + промпты): как декомпозировать, когда спрашивать,
когда эскалировать, когда перепланировать, критерии готовности.

**Эскалация тиров.** junior → middle → senior по: провалу проверок критика,
явному сигналу диспетчера, повторным неудачным попыткам. Стоимость учитывается
при выборе тира.

**Проверки критика.** Критик не требует фиксированного набора команд: он
запрашивает у агента доступные возможности (языки, сборщики, линтеры) и
использует только их. Нет инструмента — проверка пропускается, а не падает.
Критерии выводятся из `Spec`.

## 9. Планировщик и стейт-машины

### Состояния PlaybookRun / Task
```
pending → ready → running → waiting_dependency
                          → waiting_user
                          → review
                          → done | failed | cancelled
```

- **waiting_dependency** — ждёт `dependency`/`data`-рёбра.
- **waiting_user** — human-gate; **не блокирует** соседей.
- **review** — на проверке критика.

### События планировщика
`NodeReady`, `NodeStarted`, `NodeWaiting`, `NodeBlocked`, `NodeReview`,
`NodeDone`, `NodeFailed`, `NodeCancelled`, `PlanRevised`.

### Свойства
- Квоты параллелизма: per-session / per-tenant / global.
- **Чекпоинт после каждой задачи**: состояние + артефакты в БД.
- **Идемпотентность** внешних вызовов (idempotency key).
- **Disconnect policy**: сессия → `paused`, все `running` → `paused`; при
  реконнекте — resume с последнего чекпоинта, reconcile in-flight вызовов.
- **Перепланирование**: план event-sourced; мутации — команды с валидацией
  инвариантов; текущий граф — проекция. Ограничители: бюджет, лимит шагов,
  «стабильность плана» (анти-дребезг).

## 10. Протокол ядро ↔ агент

Кастомный бинарный/JSON WS, **мультиплексированный**.

- **Handshake**: `hello`/`welcome` с версией протокола и **capabilities**
  (OS/arch, shell, языки, git, список MCP-серверов) → попадает в контекст ролей.
- **Фреймы**:
  - control: `ping/pong`, `resume(from_seq)`, `error`
  - session: `session.open/close`
  - plan: `plan.update`
  - task: `task.assigned/progress/result`
  - tools: `tool.call/result`
  - events: `event.append(seq)`
  - human: `question/answer`
  - data: `artifact`
  - meta: `usage`
- **Гарантии**: at-least-once + idempotency keys; ack; resume по seq.
- **Flow-control**: bounded buffers + коалесинг токен-дельт (дельты опциональны).
- **Кодировка**: JSON сейчас, CBOR/permessage-deflate позже.
- **MCP** остаётся транспортом инструментов, не control-plane.

На этапе P0 агента нет — используется in-process fake transport в тестах.

## 11. Инструменты и MCP

Реестр инструментов с `kind`:

| kind | Где исполняется | Примеры |
|---|---|---|
| **internal** | в ядре | web_search, калькулятор, retrieval, read-only анализ |
| **agent** | на машине пользователя (через WS) | fs read/write, exec, git, браузер |
| **remote** | внешний HTTP MCP | сторонние MCP-серверы |

- В ядре — только безопасные/read-only инструменты; пользовательский код не
  исполняется.
- MCP-серверы, объявленные агентом в handshake, вливаются в тул-листы ролей.
- Каждый вызов инструмента: права, таймаут, лимит вывода, аудит.

## 12. Хранилище

**Postgres** — источник истины:

- `tenants`, `users`, `devices`, `projects`
- `sessions`, `specs`
- `plans`, `plan_nodes`, `plan_edges`
- `playbooks`, `playbook_runs`
- `tasks`, `task_attempts`
- `messages`, `questions`, `answers`
- `artifacts` (метаданные + ссылка)
- `events` (append-only, партиционирование по времени)
- `jobs` (durable-очередь исполнения: lease/heartbeat/attempts)
- `usage`, `idempotency_keys`

### Stateless-исполнение (реализовано)

- API только **enqueue**: ответ 202; job kinds: `run_plan` (исполнение плана),
  `interview` (интервью, старт/ответ) и `plan` (LLM-планирование из спеки).
- Воркеры забирают job через `UPDATE ... FOR UPDATE SKIP LOCKED` (безопасно при
  любом числе реплик), ставят **lease** и шлют **heartbeat**.
- Если воркер упал, lease истекает, job забирает другой воркер, **reconcile**
  сбрасывает узлы `running → ready`, и план продолжается (состояния узлов
  персистентны → возобновляемо).
- Ошибка/провал плана → job `requeued` до `max_attempts`, затем `failed`.
- Так API и воркеры можно масштабировать горизонтально на общем Postgres.

**Object storage** — крупные артефакты: диффы, логи, сгенерированные файлы, трейсы.

**Redis** — pub/sub для live-фан-аута, распределённые локи, rate-limit; на старте
часть можно заменить на Postgres `LISTEN/NOTIFY`.

Храним всё без ретеншена на старте; политику ретеншена определим позже.

## 13. Multi-tenancy и безопасность

- Row-level изоляция по `tenant_id`.
- Квоты и бюджеты на tenant/session (стоимость, параллелизм, токены).
- Секреты провайдеров — только в ядре (secret store), агенту не уходят.
- Аутентификация агента: **самописные device-токены** (создание → pairing →
  короткоживущие сессионные токены), TLS.
- Аудит всех мутаций плана и вызовов инструментов.
- В ядре не исполняется пользовательский код.

## 14. Наблюдаемость

- Структурные логи.
- OpenTelemetry: трейсы на задачу/tool-call/LLM-вызов.
- Метрики: латентность, стоимость, токены, глубина очередей, ошибки, ретраи.
- Проекции из event-log: граф, таймлайн треда, история MCP/диалогов,

## 15. Eval

Eval — «тесты для агента»: измеряют качество плейбуков и ловят регрессии.
Это **отдельный контур ядра**, не поле шаблона плейбука.

- **Fixtures** — стартовое состояние (репо-снапшот/пустой проект/требования).
- **Checks** — определяются самим eval-кейсом (не плейбуком) и используют
  только те инструменты, что доступны в окружении; затем LLM-judge по рубрике.
- **Метрики**: pass-rate, стоимость, латентность, число перепланирований,
  вмешательств человека, итераций критика.
- **CI**: прогон при изменении плейбука/промпта/модели; сравнение с baseline и
  гейт на регрессию.
- **Траектории**: полный лог задач/вызовов для отладки и replay.

Пример: eval-кейс «Backend API», fixture = репозиторий с пустым сервисом,
checks = сборка/тесты/валидация OpenAPI **если соответствующие инструменты
доступны**, плюс рубрика по спеке. Падение pass-rate с 80% до 60% после правки
промпта блокирует релиз.

## 16. Структура модуля

```
conclave-core/
  go.mod                       # module github.com/texhik/conclave/conclave-core
  PLAN.md                      # этот документ

  internal/
    config/                    # env/конфиг, DSN, секреты

    plan/                      # граф, версии, мутации, валидация
    scheduler/                 # переходы, параллелизм, квоты, чекпоинты, reconcile
    orchestrator/              # interviewer, planner, supervisor, dispatcher, critic, router
    playbook/                  # реестр шаблонов, версии, loader
    llmgw/                     # провайдеры, routing, fallback, бюджет, usage
    toolgw/                    # internal tools + прокси external + реестр
    mcp/                       # internal/remote MCP-клиенты
    session/                   # жизненный цикл, вопросы, политики
    store/                     # postgres-репозитории, миграции, tx
```

## 20. Принятые решения (decision log)

| # | Решение | Обоснование |
|---|---|---|
| 1 | Отдельный Go-модуль `conclave-core/` в этом репо | greenfield, независимые зависимости |
| 2 | `conclave-agent/` — отдельный модуль | разделение core/agent |
| 3 | Postgres как источник истины | надёжность, партиции, SQL |
| 4 | Самописные device-токены | простота на старте, контроль |
| 5 | UI и агент сейчас не делаем | фокус на ядре |
| 6 | Плейбук = supervisor + опциональный явный граф | гибкость + воспроизводимость |
| 7 | Храним всё без ретеншена | отладка/eval, политику позже |
| 8 | Иерархия контроллеров вместо одного | контекст, стоимость, масштаб |
| 9 | Два уровня графа | читаемость, разделение контекста |
| 10 | Human-gate не блокирует siblings | параллелизм |
| 11 | Disconnect = пауза + reconcile | устойчивость к разрывам |
| 12 | MCP — транспорт инструментов, не control-plane | чёткое разделение |
| 13 | Всё в облаке | единая инфраструктура, качество |
| 14 | Eval — отдельный контур ядра, не поле плейбука | измеримость без жёстких критериев в шаблоне |

## 21. Глоссарий

- **Плейбук** — переиспользуемый шаблон процесса (BA, backend, …).
- **Плейбук-ран** — запущенный экземпляр плейбука (тред).
- **План** — версионируемый граф плейбуков для сессии.
- **Спека** — требования/ограничения/acceptance, собранные интервью.
- **Задача** — единица работы внутри плейбука.
- **Диспетчер** — компонент, раздающий задачи ролям-тирам.
- **Критик** — проверяющий объективно и по спеке.
- **Human-gate** — ожидание ответа/одобрения пользователя.
- **Reconcile** — сверка незавершённых вызовов после реконнекта.
- **Eval** — автоматические «тесты агента» для измерения качества.
